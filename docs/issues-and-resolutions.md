# Observed issues, resolutions and remaining limits

Updated 2026-11-17. Evidence sources: saved local traces summarized in local-model-troubleshooting.md; controlled B01 study; five-task study 6372f9258614472f8f8bf2945a998605. Observations describe the tested versions/configurations, not every LLM. The 1,200-case study had 801 attempted cases and 399 quota-skips. OpenRouter contributed a quota rejection and skips, not new model-performance evidence.

| Issue found | Resolution implemented | Remaining limitation / verification boundary |
|---|---|---|
| Architectural claims lacked evidence of useful completed agents | Published fixed-task studies, full traces, scored outcomes and live tool-integration smoke observations distinguish demonstrated behavior from roadmap/design | Synthetic baselines and one units example do not establish production readiness or useful autonomous operation in a real deployment |
| Earlier tool-like XML/prose could be treated as a final answer | ReAct parser rejects common unrecognized tool-call forms, multiple actions and invented observations; native schemas/results use a normalized action contract | Prompt-only models still need format compliance; no growing collection of model-specific XML parsers is presented as universal support |
| Experimental threads/tools were unsuitable evidence of safe equipment control | Credential vault, sensitive-path and allowed-directory checks, safe text writes, explicit MCP server/tool allowlists, execution records and documented uncertain timeout effects | No operating-system sandbox, equipment-control certification or unrestricted Home Assistant deployment is claimed; those require a separate scoped implementation and evaluation |
| Choosing a model/catalog entry did not establish that it was loaded; repeated inventory looked like activity | Current Choose model workflow discovers available models, unloads/replaces local text models and verifies activation; catalog and task execution are separate | Provider and hardware availability still matter; a ready model has not yet completed inference |
| Confusing refresh/load/status controls and multi-model handling | Unified model picker and up to ten workspace model slots | Local model leases/resource limits differ from cloud routing; native backend behavior is not identical |
| Repeated model-list traffic without a useful run indication | Model catalog caching, explicit selection, live task/run status and traces | A models-list response proves discovery only; do not call it inference success |
| Missing, invalid or stale API credentials | Encrypted native OS credential vault, Secrets & API inventory, provider portal links, explicit access/operation tests and review dates | Key presence/one accepted operation does not establish quota, billing, every model or every tool operation |
| Free API quota exhaustion interrupted comparisons | Checkpointed study accounting distinguishes attempted, rejected and skipped; no paid/model fallback in the study | Quota skips are not model failures or performance observations |
| Search returned errors, irrelevant snippets or repeated identical calls | Provider diagnostics, existing read caching/loop guards, explicit free/frozen-source testing; universal gateway classifies operational failures | Live search changes; configured auto search can use provider credits; no-results is not proof a document does not exist |
| Baseline tests lacked obvious start/progress/completion and accessible failure reasons | Live run status, per-case details, traces, history and saved run IDs | Completed scheduling is distinct from strict task success; always inspect the selected saved run |
| Saved run settings differed from current URL/form | Documentation and saved-run/configuration separation; deliberate settings-copy workflow | A URL's next-run fields do not rewrite the stored experiment |
| Models calculated wrong totals or gave unstable numeric answers | Portable Qalculate tool: LLM proposes formula/values, actual engine computes; exact/string results and graph records preserved | Formula/input interpretation may still be wrong; no universal mathematical deficiency was established |
| Calculator arguments contained scripts, report JSON, invalid expressions or missing fields | Narrow math interface, full JSON Schema validation before every tool; bounded 50-digit Decimal basic calculator; scientific engine checks diagnostics | A model can still fail to form a valid request; recovery is bounded by run limits |
| qalc terse output hid division-by-zero warnings | Diagnostic evaluation precedes raw-result extraction; failures are structured; plotting records domain warnings/gaps | Sampled plots do not prove continuity; exact and approximate output differ intentionally |
| Correct tool computation followed by malformed/incorrect final output | Verified tool_result records are separate from truncated observations and final prose; common execution IDs and complete bounded outputs | Free-form final-answer faithfulness is not automatically guaranteed; stage-specific evaluations remain necessary |
| Groq GPT-OSS direct answers were strong while tool-arm calls hit tool_use_failed | Native OpenAI-compatible tool schemas/call normalization plus explicit prompt/native mode; no silent billable fallback | Application transport tests validate mechanics; a new matched live model study is needed to measure the change |
| Tool arguments/results/status differed by entry point and provider | Shared UACP ToolGateway, explicit per-tool contracts, standard result envelope; in-process/MCP paths share code; external MCP allowlists and namespacing | MCP standardizes communication, not model decisions; provider-specific adapters remain |
| Tool calls could time out with uncertain execution state | Explicit timed_out/may_still_be_running; concurrency capacity held; no automatic retries; qalc child termination | Generic Python threads and remote effects cannot be forcibly cancelled safely by this layer |
| B02 accepted Sunday but rejected Sundays; complete source-coverage requirement could dominate otherwise correct facts | Published supplemental rubric analysis and evaluator limitations; historical scores remain intact | A versioned semantic scorer/pilot is still needed; no retrospective score correction is claimed |
| B05 otherwise-correct explanations failed an unstated requirement to include both 12 and 10 in prose | Published exact rule/limitations and preserved evidence | Future prompts/scorer must align explicitly; baseline-v1 is unchanged |
| Large single/team comparisons could conflate limits or repeated failures with reliability | Shared task budgets, fixed fixtures/seeds, independent repetitions, controlled arms and per-stage error evidence | Cache/provider/environment changes remain uncontrolled where documented; repeated failure is not reliability |
| C: filled during studies and development | Study data, calculator runtime/artifacts and verified test environment on D:; cleared regenerable pip cache | Monitor disk availability; no project/user source was discarded. Locked old test-environment remnants are retained under ignored test scratch |

Successful tool execution is not sufficient for a correct final report. November 18 recovery fixes: provider finish_reason=length now rejects partial text/actions for bounded format recovery, rather than normalizing truncated prose as success. Unchanged read_fixture calls are cached per run; repeated attempts receive explicit finish/recovery feedback and stop after four identical requests instead of repeatedly executing the read. Baseline final answers receive a maximum of one correction opportunity for JSON/required-field failures and B01 field types or totals consistency. The validator does not consult fixture answers; consistent but factually wrong reports still fail the unchanged scorer. Rejected candidates are retained in the trace. B01 runtime guidance clarifies refund signs per category and numeric calculator expressions. Original fixtures, expected values, rubric and saved runs remain unchanged; new adapter behavior/guidance makes these follow-ups distinct from historical runs.

Baseline checkbox layout now places boxes beside labels and groups tools on their own row. Disabled boxes under automatic setup are intentional; switching automatic setup off makes tool selections editable, and switching it back on restores required tools.
